# M2 结果：规则控制器没有跑赢静态档

> 预注册的验收线（`docs/ADAPTIVE-DESIGN.md` §9）：控制器必须在线逼近 oracle，
> 且**不得劣于最好固定 profile**。本轮结论：**未通过**。

## 实现

- 窗口级控制器（`crates/lacbs-core/src/controller.rs`）：每 60 s 模型时间收一次窗口统计，
  选 P0（不拒绝、晚服务）或 P4（拒绝 + 抢占 + 老化），初始档固定为 P4（最优静态档）。
- 信号：`util = 本窗到达数 / 历史最大处理数`（容量自适应估计）；
  `util > 0.95` 或 `max_wait > 1 s` → P4；`util < 0.5` → P0；中间保持。
- 安全层：连续 3 个窗口一致才切、切换后冷却 2 个窗口；切换次数 ≤ 窗口数（门禁断言）。
- 评估：预注册的 6 条 ServeGen 轨迹、同一把尺、两种计价口径。

## 结果（分数 = 达标数 − penalty × 拒绝数；越高越好）

| 轨迹 | 静态 P4 (p1) | 控制器 (p1) | oracle (p1) | 控制器 vs 静态 |
|---|---|---|---|---|
| A1 m-large | 1621 | 1589 | 1798 | **−2.0%** |
| A2 m-mid | 1993 | 1850 | 2096 | **−7.2%** |
| A3 reason | 982 | 924 | 1036 | **−5.9%** |
| B1 m-small | 2027 | 2027 | 2192 | 0.0%（0 次切换） |
| B2 m-large alt | 810 | 680 | 983 | **−16.0%** |
| B3 reason alt | 689 | 597 | 690 | **−13.3%** |

纯达标口径（penalty=0）方向一致：A1 −0.6%、A2 −4.8%、A3 −3.2%、B1 0.0%、B2 −6.9%、B3 −6.0%。

**6 条里 5 条变差、1 条打平，没有一条变好。**

## 为什么失败

1. **"空闲"信号不可靠**：队列里堆的是"等待被拒绝的无望请求"，长度常在两三千；
   用它判压力必然误判。改用 `util = 到达 / 最大处理量` 后能切了，但突发刚过时 util 仍低，
   控制器切到 P0，积压随即反弹（A1 最大等待 49 s，B2 81 s）。
2. **切到 P0 的收益本身是计价假象**：在 calm 阶段，P0 只是"不拒绝、让请求晚点超时"，
   每个被拒请求 −1、每个超时请求 0，所以 P0 分数更高；它并没有多服务成功多少。
   控制器去追这个 gap，等于主动选择"软失败"而不是"快速失败"。
3. **切换代价被低估**：60 s 窗口 + 3 窗确认 = 决策滞后 ≥180 s，而 ServeGen 的阶段只有 600 s。
   等控制器确认"现在是 calm"，阶段已经过去一半。

## 判定

- **M2 不上线**：规则控制器在真实/生成轨迹上系统性劣于静态 P4。
- **静态 P4 仍是默认**（在这批负载上它是 4/6 轨迹的最优固定档）。
- 方向再次收口：除非换一种**每请求**的判据（例如按剩余 slack 决定"拒 vs 晚服务"，
  而不是按窗口聚合切 profile），否则"窗口级规则切换"没有证据支持。

## 遗留

- 门禁第 7 步只断言"能跑完 + 切换次数 ≤ 窗口数"，不判断优劣——优劣需要 oracle 对照，成本高。
- 若要继续，最小可信实验是：**逐请求的 slack 策略**（单请求维度的拒/等决策），
  在同样 6 条轨迹上与 P4 对比；这已经不是"profile 切换"，而是新的策略族。
